lamarck: Pre-Registered Studies of Self-Improving LLM Agent Harnesses

Jiaju Zhang
Northeastern University
github.com/xungirl/lamarck
Code ↗Study 3 results ↗Pre-registration ↗Evidence ↓

Abstract—Can an LLM improve the harness around an agent, and does a memory of past edits help? lamarck is an open implementation of Self-Improvement Memory (SIM), whose paper ships no code, on an evolutionary code-harness engine: an LLM proposer edits prompts, configuration and control code, each candidate is a git branch evaluated in a gVisor sandbox, and a gateway prices every call in RMB under a hard cap. In three text-to-SQL studies run under a pre-registered plan (deviations disclosed), the model that edits the harness matters: with qwen4-max as proposer and selector, a fixed-n replication found +3.75 held-out points (n = 10, one-sided p = 0.0046). SIM produced no conclusion: at pilot scale its effect could not be told apart from zero.

Index Terms—recursive self-improvement, LLM agents, pre-registration, gVisor, budgeted LLM gateway.

I. The problem

Small effects, noisy scores

In harness self-improvement an LLM rewrites the code and prompts around a policy model and keeps the edits that score better. SIM (Yu et al., arXiv 2611.18856) adds optimizer-side memory: each accepted edit is filed by root cause with the tasks it was predicted to fix, and carried over when the benchmark changes. Two questions: does SIM beat carrying only the evolved harness, and is the search model a bottleneck? Scores move a few tasks at a time, so the design is built to keep the experiment honest: held-out tasks never reach the search, predictions are sealed before evaluation, and PREREG.md was committed before the first experiment.

II. Design

The engine keeps each candidate on its own git branch and worktree and accepts it by fast-forward. Per round it evaluates the incumbent, drafts proposals in parallel, runs a deterministic critic and an LLM screen, evaluates the survivors, and admits only candidates that pass a noise band calibrated from three evaluations of the starting harness and a cost rule. Each evaluation runs in a fresh gVisor (runsc) container with a read-only root, no capabilities and an internal network whose only peer is the gateway; the escape probes (external IPs, DNS, cloud metadata, the Docker socket, raw sockets) all fail.

The gateway is the only holder of the API key. It reserves a worst-case price before each call, settles from the returned usage and refuses any call that would cross the cap. A scheduler starts a run only if the money left covers it and every higher-priority run.

III. Results

Study 3 repeated Study 2 with fresh seeds (21-30) at a fixed, pre-registered n. All ten runs finished; mean held-out change +3.75 points, 95% CI [+1.19, +6.31], and by the pre-registered rule the verdict is: replicated. Against seven flash-search controls the gain was +3.75 (Welch p = 0.031), but those controls ran a day earlier and were not randomized.

For SIM, Study 1 (Spider → BIRD, qwen3.8-flash in every role) found Δ = 0.0, −10.0, +5.0 points in the three primary pairs. A secondary extension to seven pairs, added after the primary result was seen, gave −1.07 (95% CI [−5.3, +3.1]). That interval contains both zero and the SIM paper's +2.36, so it neither supports nor refutes SIM.

IV. Limits

This is pilot scale: one task is 2.5 points on 40 held-out tasks, and repeat evaluations of one harness at temperature 0 differ by about as much as the effect. One model family, one benchmark, 3 rounds. A provider credit outage stopped Study 3 at five runs; completing it to the pre-registered ten was decided after the interim result (+3.5, one-sided p = 0.026) was visible, with no rule changed. SIM was tested only with the flash search model, and 6 of 7 Spider-evolved harnesses started below the seed harness on BIRD. The cross-model condition was not run with real models. Whether SIM helps remains open.
