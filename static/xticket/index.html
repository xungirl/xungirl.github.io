Xticket: A Microservice RAG Assistant for Support Tickets, Measured Before It Was Tuned

Jiaju Zhang
Northeastern University
github.com/xungirl/Xticket
Code ↗Evidence ↓

Abstract—A support agent facing a new ticket wants to know how similar tickets were solved before. Xticket is a three-service RAG app (Next.js UI, FastAPI gateway with JWT and chat history, FastAPI + LangChain agent over Weaviate and Ollama) whose answers stream token by token and cite the historical tickets they used. Before changing anything, a benchmark was built: 77 hand-labeled queries, 14 retrieval configurations and 4 end-to-end variants. It showed the English-centric embedding model was the root cause of poor retrieval, and switching to a multilingual one took Recall@5 from 68% to 100% (hard set 44% to 100%). It also found that the system prompt was never sent; fixing that and allowing only retrieved IDs cut p50 latency from 18.0 s to 6.8 s and brought fabricated citations to 0%. The corpus is only 25 tickets, so absolute scores are optimistic.

Index Terms—retrieval-augmented generation, embedding evaluation, Weaviate, Ollama, LangChain, server-sent events, FastAPI, Next.js.

I. The problem

A working app that nobody had measured

The starting point was a working three-service course codebase; the gateway scaffold in server/ came from a course template. The question was whether its answers were grounded in the right tickets, and nothing measured that. So the first step was a measuring stick: benchmark.py with sweep, ingest and e2e modes, and 77 hand-labeled queries. The dev set (25) is paraphrases for tuning; the test set (25) was written before any results and never used to choose; the hard set (27) has near-duplicate tickets, slang, typos and English questions. The selection rule was fixed in advance: highest dev MRR, then hard MRR, then lowest latency.

II. Retrieval

The sweep crossed 3 embedding models with 3 ways of building the indexed text, plus a task prefix, an instruction prefix and hybrid BM25 + vector at α = 0.25 / 0.5 / 0.75. With the original model, one ticket (TK010) was the top hit for 24% of dev queries (hubness). Multilingual models fixed this; config I won by the pre-set rule. Only the embedded text changed: the LLM still receives the full ticket. Hybrid search was a negative result: trigram BM25 is noisy on short colloquial Chinese, so it was not adopted. Retrieval p50 rose from 9 ms to 30 ms, small next to multi-second generation.

III. Generation

Four variants went through the real SSE endpoint. The system prompt ("don't fabricate", "cite ticket IDs") was defined in config but the chain used only the QA template; sending it (v2) took correct citations to 100% but 28% of answers cited IDs that were never retrieved. Prompt v3 lists the retrieved IDs and allows only those. Every request also retrieved twice, once for sources and once inside the LCEL chain; the chain now takes the retrieved context. Output speed stayed at 25–27 tokens/s in all four runs, so the speed-up came from shorter answers (395 → 167 tokens p50), not a faster model. A fingerprinted index cut warm restart from 4.9 s to 2.4 s; batch embedding was only 4–6% faster (negative result).

IV. Limits

The corpus is 25 tickets and the queries are self-written, so absolute scores are optimistic; the relative gains and the bugs found are the point. The strong models scored 100% on dev and test (a ceiling effect), which is why the hard set was added afterwards. Each e2e config ran once on one laptop, and p95 is sensitive to single long answers. Time-to-first-token swung 0.2–2.5 s with Ollama's prompt cache and is not used as a result. Citation accuracy is a regex match on ticket IDs, not a judgment of whether the answer is correct. pytest tests -q reports 11 passed, including a retrieval gate that fails if dev or hard Recall@5 < 95% or MRR < 0.90 (needs local Ollama). Weaviate is 1.30.5 embedded locally but 1.27.1 in docker-compose. Xticket was a Northeastern CS course project (Spring 2026); the benchmark, eval sets, fixes and tests are the author's own work.
