raft-kv: A Linearizable Key-Value Store on Raft, Built from Scratch in Go

Jensen Zhang
Northeastern University
github.com/xungirl/raft-kv
Code ↗Benchmarks ↗Evidence ↓

Abstract—raft-kv is a replicated key-value store on a from-scratch implementation of Raft in Go, using only the standard library. Every Get, Put and Delete goes through the Raft log, writes are de-duplicated by (ClientID, Seq), and the log is a CRC-checked write-ahead log fsynced per batch. In a chaos run with 59 leader kills, 25 other kills and 9 full-cluster kills, all 20,007 acknowledged writes were read back, 0 lost. After the leader is killed, a new leader is visible at a median of 243.6 ms, group commit lifts 64 clients to 2,554 ops/s, and 260/260 test runs passed under the race detector. All performance numbers come from 3 to 5 processes on one laptop over localhost.

Index Terms—Raft, consensus, linearizability, write-ahead log, group commit, fault injection, Go.

I. The problem

One log, agreed on while nodes crash and messages get lost

A replicated store is only useful if a write the client was told succeeded is never lost, and if no read returns stale data. Raft gives the rules: one leader per term, replicate entries, commit once a majority has them. The rules are easy to get subtly wrong. A stale leader in a minority partition still accepts commands, a delayed AppendEntries can erase newer entries, and an entry from an earlier term can look committed when it is not (Figure 8 of the Raft paper). raft-kv implements the algorithm from the paper and then attacks it with simulated message loss and partitions, and with real SIGKILLs.

II. Design

Raft core. Leader election with randomized timeouts (150–300 ms), 50 ms heartbeats, replication with the AppendEntries consistency check and fast conflict backtracking, and a commit rule limited to current-term entries. A new leader appends a no-op so that earlier entries commit at once. One mutex guards each node and is never held across peer I/O, and each follower has at most one AppendEntries in flight.

Durability. Term, vote and log are persisted before replying to any RPC. The log is an append-only WAL of [len][crc32][term][index][cmd] records, and on startup everything after the last valid record is cut off. One small write plus fsync costs 4.25 ms on this disk, so persistLogLocked covers every pending entry with one write and one fsync (group commit).

KV service. The server submits each request with rf.Start and answers once that index is applied. Reads go through the log as well, so a deposed leader cannot return stale data. A Clerk retries with the same Seq, and the state machine skips any write with Seq <= lastSeq[ClientID].

III. Verification

Tests swap the TCP transport (net/rpc) for simnet, so the same Raft and KV code runs under ~10% request and ~10% reply loss, replies delayed by up to 700 ms, partitions and 300 rounds of random crashes. The harness checks on every apply that no two nodes apply different commands at one index, and a Wing & Gong checker validates concurrent histories. Two hand-applied mutations (output not saved) show why targeted tests exist: disabling dedup made TestKVExactlyOnce fail with 624 writes applied instead of 500, and serving Get locally made the stale-read test fail. The randomized linearizability test caught neither in 4 runs each.

Under go test -race -count=10, 260/260 runs passed with 0 data races. The first such run found a bug in the test harness, not in Raft: it submitted commands to a stale minority leader, so one partition test took 108.8 s on later iterations. It now takes 8.8–10.9 s.

One client pays for two fsyncs in series, leader then follower. With 64 clients, throughput is ~32× higher while p50 only doubles, because one fsync covers a whole batch. Five nodes are slower in every column: they need three acknowledgements and share one SSD. After a leader SIGKILL the first client write succeeds at a median of 253.1 ms. The slow tail (8 of 25 trials above 370 ms) is probably split votes, a hypothesis not confirmed from node logs.

V. Limits

There are no snapshots or log compaction, so a restarted node replays the whole log. Membership is static, there is no PreVote or CheckQuorum, reads cost a log write, and AppendEntries is not pipelined. fsync runs under the Raft lock. Moving it into a goroutine that still held the lock dropped 64-client throughput from 2,426 to 841 ops/s in quick 3 s runs (raw output not saved), so the change was reverted. SIGKILL tests process crashes, not power loss, and loopback numbers say nothing about real network latency.
