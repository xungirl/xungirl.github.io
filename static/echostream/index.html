echostream: A Distributed Short-Video Recommender

Jiaju Zhang · Northeastern University · github.com/xungirl/echostream

Every swipe echoes. 每一次划动，都有回响。

A short-video recommendation system: a scaled-down TikTok-style feed on Kuaishou's real KuaiRec data. A client asks what user 42 should watch next and gets a ranked list; a watch or a skip changes the very next refresh.

Code ↗Benchmarks ↗MVP report ↗Raw results ↗Evidence ↓

Abstract—echostream is a scaled-down replica of the architecture behind a short-video “For You” feed, built on KuaiRec, a real interaction log from Kuaishou. A request runs five recall paths at once, including a two-tower ANN query scattered over 4 index shards × 2 replicas under a deadline, then a LightGBM ranker and optional MMR; a watch or a skip flows through partitioned Redis Streams into a sharded feature store and changes the very next answer. Recall plus ranking reaches NDCG@10 0.1100 against 0.0430 for the best baseline. All 12,530,806 real events replayed at 37,221 events/s with 0 users mismatched, 15 fault-injection runs kept 100% availability, and /recommend held p99 26.3 ms at 200 req/s. Everything runs as multiple processes on one laptop, and the weaknesses found along the way are reported below.

Index Terms—recommender systems, two-tower retrieval, logQ correction, LightGBM ranking, scatter-gather, Redis Streams, exactly-once effect, chaos testing, KuaiRec.

I. The problem

A feed that answers in milliseconds and listens to every swipe

A short-video feed must answer “what should this user see next?” within a strict latency budget, and a watch or a skip should change the very next answer. echostream rebuilds that loop as a backend service on KuaiRec, released by Kuaishou: 12,530,806 interactions from 7,176 users on 10,728 videos, not synthetic data.

Honest scope. Every “node” is an OS process on one 8-core Apple M2 laptop: multi-node on localhost. Fault tolerance, tail latency and event reliability are tested for real; horizontal throughput scaling is not claimed. Each number is labeled quality (recommendation metrics on real data), real-replay (systems numbers driven by the real event log), systems (real users and model, scheduled requests) or synthetic (random vectors).

II. Design

Read path. Recommender._pipeline runs under a 250 ms deadline that every stage inherits (Fig. 1): real-time features from the user's feature node, a numpy user tower, then five recall paths at once — the two-tower ANN query fans out to every shard while ItemCF, two popularity paths and a caption-content path for cold videos run locally — a quota merge, a LightGBM ranker over 40 features and optional MMR. A slow or dead dependency produces a labeled, degraded answer instead of an error.

Write path. POST /events appends to one of 8 Redis Streams partitions chosen by the user id. Four workers lease partitions, so one owner keeps each user's events in order; a Lua script on the user's feature node deduplicates and applies an event in one atomic step, an exactly-once effect over at-least-once delivery.

Tooling. A ~400-line process supervisor replaces docker compose, so tests can kill, freeze or slow any process in milliseconds with no VM network inside the latency numbers; nginx retries the other API replica on errors.

III. Results

On the temporal test split, recall plus LightGBM reaches NDCG@10 0.1100 [0.1064, 0.1136], +0.0297 over recall-only ordering (paired CI [0.0267, 0.0325]). The two-tower's logQ correction carries most of the retrieval gain: 0.0803 with logQ, 0.0071 with neither logQ nor mixed negatives, 0.0795 with both.

Under faults. Five fault types at 100 req/s, three runs each — kill a shard primary, slow a shard by 500 ms, kill a worker, freeze a feature node, kill an API replica — kept 100% availability: 0 of 67,500 requests failed. Freezing one of three feature nodes degrades the users it owns (33–37% of responses carry feature_store_unavailable) instead of failing them (Fig. 3).

A. The write path at full speed

Replaying all 12,530,806 events in their original order through nginx, the API, the streams and the workers ran at 37,221 events/s end to end; afterwards 0 of 7,176 users had a counter that differed from the parquet ground truth, with 0 duplicates and 0 dead letters (Fig. 4). Paced at 10,000 events/s, event-to-feature latency stayed in the ≤ 50 ms histogram bucket at p99.

IV. What did not work

Multi-path recall. With quotas chosen on the validation phase, the merged candidates recall less than the two-tower alone on test (recall@200 0.233 vs 0.271). It was not re-tuned on test.

Exposure bias. On the fully-observed small matrix, ItemCF beats the two-tower (NDCG@10 0.618 vs 0.402).

Offline vs simulated online. In a pre-registered simulated A/B on 1,411 fully-observed users, the ranker did worse than the two-tower alone (−0.034 positives per impression, CI [−0.037, −0.030]), and test NDCG@10 ordered the five variants with Kendall τ = −0.4 against the simulated online order.

Protocol revised after looking at test. The first ranker lost to recall-only ordering on test (0.0696 vs 0.0803); the training protocol behind 0.1100 was designed after that result. Both runs are kept.

Cache. A per-user cache under Zipf traffic hit 71.7% and cut p50 from 10.3 to 3.1 ms, but p99 rose from 21 to 81 ms.

V. Limits

Latency numbers share 8 cores with the load generator and about 20 other processes; 250 req/s saturates the laptop. The dataset would fit one process; the distributed parts exist to build and measure the mechanisms. Synthetic scale tests (1M–10M random vectors) measure latency and memory only: per-shard memory falls with more shards, but p50 rises from 2.3 to 6.0 ms from 1 to 8 shards on one machine. “Liked” is a proxy (watch_ratio > 2) that favours short videos, the simulator replays true watch ratios rather than live users, and KuaiRec has no video files, so the demo shows cards, not playback.
