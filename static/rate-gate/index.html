rate-gate: A Distributed Rate-Limiting API Gateway in Go

Jiaju Zhang
Northeastern University
github.com/xungirl/rate-gate
Code ↗Benchmarks ↗Evidence ↓

Abstract—A rate limit only means something if every gateway instance agrees on the count. rate-gate is a reverse-proxy gateway in Go that identifies each caller by API key, user ID or IP and enforces per-route limits with four algorithms (token bucket, fixed window, sliding window log, sliding window counter), kept in process memory or in Redis. With Redis, each decision is one atomic Lua script on Redis server time, so 3 gateway instances allowed exactly 10,000 of 10,000 expected requests (9,990 for the sliding counter) while 59,994 were offered; the in-memory backend allowed ~3x. At 64 connections the in-memory limiter was within run-to-run noise of the bare proxy (42,939 vs. 43,366 req/s), and one in-memory decision takes ~40-150 ns with 0 allocations. All numbers come from one Apple M2 laptop over localhost.

Index Terms—rate limiting, API gateway, Redis Lua, token bucket, sliding window, circuit breaker, Go.

I. The problem

Why a shared limit is hard

A rate limit is a read-modify-write: read the count, decide, write it back. With several gateways in front of one service, doing this as separate commands lets two instances both read "99 of 100 used" and both allow, so the limit is exceeded under concurrency. Using each gateway's own clock adds a second failure: clock skew between hosts makes them disagree about which window it is or how many tokens have refilled.

The algorithms also differ. A fixed window can admit up to 2x the limit in a short span across a window boundary. TestBoundaryBurst sends 10 requests at t=0.9 s and 10 at t=1.0 s against a 10/s limit: the fixed window allows all 20, the sliding log and sliding counter 10, and the token bucket 11.

II. Design

Every request runs one pipeline: match the route by longest path prefix, build a key from the API key, user ID, a header or the client IP, call limiter.Allow(ctx, key), write X-RateLimit-* headers, then proxy upstream or return 429 with Retry-After. All four algorithms implement one Limiter interface in both backends. In memory, state lives on a 64-shard map with a mutex per shard, and time comes from an injected Clock, so tests advance a fake clock instead of sleeping.

In Redis, each algorithm is a Lua script sent with EVALSHA. Redis runs a script to completion before any other command, so check and update are one step, and the script calls Redis TIME, so all gateways read one clock. Each client's state is one hash-tagged key with PEXPIRE. A circuit breaker (5 consecutive errors, open for 2 s, one half-open probe) wraps the Redis limiter, with an explicit policy: fail_open, fail_closed (503) or local_fallback (the default), which degrades to an in-memory limiter. Routes hot-reload on SIGHUP by swapping an immutable table through atomic.Pointer.

III. Results

Accuracy was measured open loop: three gateway processes on one Redis, four routes each limited to 1000 requests/s per API key, 6000 req/s offered round-robin for 10 s after a 2 s warm-up. The three instances together enforced the limit to within 0.1%; the sliding counter admits only while estimate + 1 <= limit, so it stays just under. With in-memory state each instance enforced 1000/s on its own, which is also what local_fallback gives when Redis is down.

Overhead was measured closed loop with a limit no request reaches, so every request pays the full limiter cost. The proxy hop dominates the overhead, not the limiter: at 64 connections the memory limiter added +0.622 ms at p50 over direct, the bare proxy +0.602 ms, and the Redis limiter, one localhost round trip per request, +2.003 ms. Tests back the atomicity claim: with a limit of 100, 100 goroutines sending 20 requests each get exactly 100 allowed, and 3 gateway instances sending 300 concurrent requests get exactly 50 allowed for a limit of 50, where the in-memory contrast allows 150.

IV. Limits

Load generator, gateway, upstream and Redis shared 8 cores over localhost, so absolute numbers would differ on separate machines; the relative overhead is the useful part. A repeat of the c=64 row came out roughly 15-26% faster with the same binary, so read any single throughput number as ±20%; the ordering held in every run. The BufferPool gain (30,647 → 52,969 req/s, proxy-only) is from single quick 3 s runs whose raw output was not saved. One Redis is a single point of contention and failure; Redis Cluster should work with the single-key, hash-tagged scripts but was not tested, and a very hot key serializes on one shard. local_fallback allows up to N× the limit with N instances. There is no TLS, auth or retries.
