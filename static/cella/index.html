cella

A Kubernetes-Native Sandbox Platform for AI-Agent Code

Jiaju Zhang · Northeastern University · github.com/xungirl/cella

CodeBenchmarks

Abstract - Code written by an AI agent has to run somewhere it cannot hurt anything, and it has to start fast. cella is a Go operator plus a multi-tenant API and MCP server that turns a declared Sandbox into one hardened, short-lived Pod and deletes it when its TTL runs out. A warm pool of pre-started Pods, claimed with a single compare-and-swap update, cuts start-up for one sandbox from 513 ms to 39 ms. All 62/62 in-sandbox isolation probes pass on runc and gVisor. In 9 controller-chaos runs on kind no sandbox got a second Pod, and a hot standby takes over in 0.8–2.1 s. The numbers come from a local kind cluster on a laptop, plus one short AWS EKS session.

Index Terms - Kubernetes operator, controller-runtime, warm pool, gVisor, NetworkPolicy, MCP, OpenTelemetry, chaos testing, AWS EKS.

I. The problem

A short-lived, locked-down home for untrusted code

An agent that writes code needs to run it right away, cut off from the host, from other tenants and from the network, and the environment must disappear afterwards. Starting a fresh container on every call puts the kubelet on the critical path: in stage 1 the controller created the Pod in ~18 ms and the remaining ~0.5 s was the kubelet. A controller crash in the middle of a burst must not leak Pods or give one sandbox two.

A. Design

Operator, level-triggered. Sandbox, SandboxTemplate and SandboxPool are CRDs validated by CEL inside the API server. Reconcile receives only a key: it re-reads the Sandbox, its template, its Pod and the clock, and computes the next step, so missed or duplicated events are harmless and a restarted controller needs no recovery logic. Pod names are deterministic, so a racing second create gets AlreadyExists. The TTL is a RequeueAfter from the stored expiresAt, backed by the kubelet's activeDeadlineSeconds.

Warm pool. A second reconciler keeps pre-started Pods ready. A claim is one Update of a warm Pod guarded by resourceVersion: it relabels the Pod and moves its ownerReference to the Sandbox. The loser of a race gets 409 and tries the next Pod; with none left, the controller creates a cold Pod.

Isolation and access. Pods run non-root with all capabilities dropped, a read-only rootfs, seccomp RuntimeDefault, no service-account token, an optional gVisor RuntimeClass and a per-template default-deny NetworkPolicy. A connect-go API (tenant = namespace, quotas) and the MCP server sit behind Envoy Gateway.

B. Results

Crashes. On kind the leader Pod was deleted 1 s after 50 Sandboxes were created at once. In all 9 runs (3 baselines without a kill, 6 with one) every Sandbox reached Running and none got a second Pod. Failover took 9.7–40.9 s with one replica and 0.8–2.1 s with a standby, so the Helm chart now defaults to 2 replicas.

Tracing found a fix. The first RunCode trace showed a 91 ms live Pod LIST on a Sandbox's first reconcile, where no Pod can exist yet. Skipping it there moved Pod creation from 104.5 to 7.0 ms after the create call.

Isolation has a price. gVisor leaves CPU loops and bulk writes at 1.0× but makes getpid 22× and stat 9× slower; 20 gVisor sandboxes at once reached Running in 8.2 s vs. 1.8 s on runc (median). The warm pool hides that start-up cost for claimable templates.

AWS EKS. In one 1.33 cluster-hour session on spot nodes, Argo CD synced the signed images and the controller was Available 20 s after the Application was created. Under three AWS FIS spot interruptions, the sandboxes on the hit node ended Failed: PodDeleted and a new gVisor sandbox was Running in 2.7–3.0 s. Destroy left 0 billable resources; the estimated cost is ≤ 1.11 USD.

C. Limits

Except for the EKS session, everything ran on a local kind cluster in a 4-vCPU colima VM on a laptop that was busy with other work; only comparisons inside one table are meaningful. runc is not a security boundary, and gVisor is not a VM boundary. On EKS the VPC CNI policy agent did not filter Pod → own-node traffic, and in mixed sequences one deny-all sandbox reached the internet in 7/7 tries: sandbox egress there needs Cilium or Security Groups for Pods. The EKS controller-kill runs had client load above the benchmark gate and could not be rerun after teardown.
