minilog

A Kafka-Inspired Replicated Commit Log in Java 21

Jiaju Zhang · Northeastern University · github.com/xungirl/minilog

CodeBenchmarks

Abstract - minilog is a Kafka-inspired replicated commit log and message broker in Java 21 with no runtime dependencies: segmented, CRC-checked logs, a binary TCP protocol on virtual threads, three-broker pull replication with an ISR and a high watermark, and a static controller that elects leaders only from the ISR. In three 120 s chaos runs with 52 random broker kill -9s, 9,634,000 acknowledged records were consumed with 0 lost, 0 duplicated and 0 order violations. Leader failover takes a median of 595 ms with a 0.5 s session timeout, a sustained producer reaches 160,075 msgs/s with 1 KiB records and acks=all, and the benchmarks exposed two latency bugs whose fixes cut end-to-end p50 from 49.5 ms to 0.27 ms. Every number was measured on one laptop over localhost.

Index Terms - commit log, replication, ISR and high watermark, leader epochs, virtual threads, chaos testing, Java 21.

I. The problem

Acknowledged must mean kept, even when the leader dies

A replicated log promises two things: a record acknowledged with acks=all survives the loss of its leader, and a consumer never sees a record that could later disappear. Both are easy to break. A leader that shrinks its ISR on its own can advance the high watermark, ack writes and then die, and the controller may elect the follower that was removed. A follower that truncates to a stale high watermark can discard committed records (KIP-101). minilog rebuilds Kafka's answers to these cases in code meant to be read top to bottom, then tries to break them with real kill -9s.

A. Design

Storage. Each partition is a list of segments: an append-only .log plus a memory-mapped sparse index with one entry per 4 KiB. Every record carries its own CRC-32C, its leader epoch and its producer sequence number, so replication and idempotence state can be rebuilt from the log itself. A torn tail is truncated on restart, and the same bytes go to disk and over the wire.

Brokers and replication. Brokers serve a binary TCP protocol (13 APIs) with one virtual thread per connection, so a long-poll fetch or an acks=all produce can simply block. Followers pull from the leader, and a follower's fetch offset doubles as its acknowledgement. The leader advances the high watermark as the ISR catches up, and consumers see nothing above it. Followers truncate by leader epoch, not to the high watermark.

Controller. One static controller process receives heartbeats every 100 ms, declares a broker dead after the session timeout (1500 ms by default), elects a new leader only from the ISR, and accepts ISR changes only through AlterIsr with a matching epoch. It also hosts the consumer-group coordinator.

B. Results

All numbers come from one Apple M2 laptop. The controller and three brokers run as separate JVMs on localhost and share 8 cores, one SSD and one page cache. Rows are medians of 3 runs unless noted. All 55 tests passed in 15 of 15 consecutive full-suite runs.

C. What the benchmarks caught

The first end-to-end run was slow even with acks=1 (p50 49.5 ms), which ruled out replication. Producer.send() woke the sender thread only for full batches, so a new batch waited for a 100 ms idle poll. A second bug left a 504 ms max with acks=all: the consumer waited for every leader's fetch, so an idle partition's 500 ms long poll held back records that had already arrived. After both fixes the acks=1 p50 is 0.27 ms. A third bug was in the benchmark: the failover clock started before the kill, so one iteration reported 0 ms. The clock now starts after the process exits.

D. Limits

The controller is a single point of failure, and consumer offsets live only on it. Consumers are at-least-once with no transactions: exactly-once consumption in the chaos runs held only because no consumer crashed, and at most one broker was down at a time. The single synchronous sender thread caps producer throughput, which is why acks=0 is barely faster than acks=1 with 100 B records. FileChannel.force was not verified to be a full write barrier on macOS. Network partitions, packet loss and multi-host latency were not tested.
