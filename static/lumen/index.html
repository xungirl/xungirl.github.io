lumen

A Self-Checking RAG Platform over New arXiv Papers, Built on the strata Search Engine

Jiaju Zhang · Northeastern University

Abstract - lumen is a RAG platform over new arXiv papers. It ingests papers every day into strata, the author's own Rust hybrid search engine, serves hybrid search and cited answers through a FastAPI service, and guards quality with fixed evaluation sets and a regression gate calibrated against measured noise. Search through the service reproduces strata's published SciFact nDCG@10 of 0.7382 to within 6e-16. Micro-batched query embeddings doubled /search throughput to 150.1 req/s at 16 clients, and ingestion survives kill -9 with 300/300 papers. Every number was measured on one laptop.

Index Terms - retrieval-augmented generation, hybrid search, score fusion, regression gate, evaluation, load testing, FastAPI.

I. The problem

Knowing whether a change made RAG better

A RAG demo is easy; knowing whether a change made it better or worse is not. An LLM at temperature 0 still varies from run to run, a search engine can behave differently once it sits behind a network service, and a nightly ingest can crash halfway. lumen treats each of these as something to measure before building on it.

A. Design

Retrieval. strata runs as an unmodified service. Its built-in hybrid mode is RRF with a fixed depth of 100, so lumen fetches the lexical and the dense list separately and fuses them with a line-by-line port of strata's fusion code. The client has per-attempt timeouts, jittered retries only for idempotent calls, and a three-state circuit breaker.

Ingestion. SQLite in WAL mode stores papers and chunks. Each fetched page and the advanced cursor commit in one transaction, and a paper is marked indexed only after strata commits it: at-least-once delivery with idempotent upserts.

Answering. /answer refuses weak retrieval before calling the LLM, numbers passages [1]..[k] and maps citations back to chunk ids. A spend ledger reserves the worst case under a file lock and settles from the returned usage. With no LLM or no budget the API returns 200 degraded with the hits; with strata down it fails fast with 503.

Gate. A change fails when any gated metric drops by more than max(3σ over 3 repeats, floor). Several metrics are gated because top_k=1 raises citation precision by +0.149 while recall falls (Table I).

B. Results

A 14-day window gave 2,764 papers in 14 API pages (fetch 39.6 s, embedding 34.9 s on MPS); re-running it fetched 0 pages. Experiments were pre-registered. Fusing top-1000 lists with α=0.3 raised dev nDCG@10 from 0.7634 to 0.7743 (bootstrap CI [+0.0039, +0.0180]), but the end-to-end RAG gain did not transfer to test (Table II).

The first load test showed /search plateauing at about 75 req/s, with query embedding taking nearly the whole latency. Batching with no wait reached 150.1 req/s at 16 clients (2.00x, a margin smaller than one std) with c=1 p50 unchanged at 14.2 ms; a 2 ms wait was rejected because c=1 p50 grew by 7.0 ms (Fig. 3). Killing strata under load gave only 503s while it was down, and the first 200 came 1.86 s after restart. 74 tests pass in 5/5 consecutive runs, and the whole project spent ¥1.5858 of a ¥3.00 cap over 1,703 LLM calls.

C. Limits

Everything ran on one laptop on localhost, shared with another workload (load average 2.6–4.8), under closed-loop load only and with a fake LLM to isolate the pipeline. The eval sets are small: 100 dev and 150 test claims, 3 repeats for the noise band, and a refusal threshold resting on 40 hand-written queries. The offline gate cannot catch prompt regressions, because the fake LLM ignores prompts. The CI workflow has not run on GitHub, the nightly LaunchAgent is not installed, and the three nightly runs found no new papers.
