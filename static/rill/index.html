rill

An LLM Inference Engine from Scratch in PyTorch

Jiaju Zhang · Northeastern University · github.com/xungirl/rill

CodeBenchmarks

Abstract - rill is an LLM inference engine written from scratch in plain PyTorch for Qwen3-0.6B, with an OpenAI-compatible FastAPI server. Its own model code (no transformers in the engine) matches Hugging Face with a max abs diff of 0.0 in fp32. Around it sit a paged KV cache with ref-counted blocks and prefix caching, an iteration-level continuous-batching scheduler with chunked prefill and preemption, seeded sampling and optional int8 weights. On one Apple M2 laptop, continuous batching reaches 377.2 tok/s vs. 305.7 static and 41.7 sequential, paged KV keeps 93.3% of reserved slots in use, prefix-cache hits cut TTFT from 359.8 to 39.6 ms, and the HTTP server plateaus at 201.4 tok/s, 3.7× a naive HF server and ~93% of Ollama's 4-bit llama.cpp.

Index Terms - LLM inference, paged KV cache, continuous batching, prefix caching, PyTorch MPS, OpenAI-compatible API.

I. The problem

Why serving is more than generate()

A naive server calls generate once per request. Each request reserves KV memory for its maximum length, and a static batch waits for its slowest member while finished slots sit idle. On this project's 64-request workload, reserving max_model_len=2048 per request keeps only 7.3% of the reserved KV slots in use, and reserving prompt + max_tokens 53.7%. Shared prefixes such as system prompts are recomputed for every request. The goal was to rebuild the core of a vLLM-style engine by hand, on a laptop GPU (MPS) that has no fused paged-attention kernel, and to measure each piece.

A. Design

The model is written block by block (RMSNorm, RoPE, GQA attention with Qwen3's q/k norm, SwiGLU, tied embeddings) over a packed token layout [T, ...], so prefill and decode rows share one forward with no padding in the linear layers. KV memory is a pool of 16-token blocks with a free list, per-sequence block tables and ref counts. New K/V go into slots with one index_copy_; attention gathers blocks into a padded batch for one SDPA call per layer.

Every LLMEngine.step() re-decides who runs: running sequences first, then waiting requests admitted FCFS under a per-step token budget (chunked prefill). When blocks run out, the newest sequence is preempted and recomputed later, since swapping frees nothing on unified memory. Full blocks are registered under a chained hash, so a new request attaches the longest cached prefix and prefills only the rest; cached blocks stay in the LRU free list, so caching never reduces capacity. The engine runs in one dedicated thread; FastAPI handlers reach it through a thread-safe inbox and per-request asyncio.Queues, with 429 back-pressure, 504 timeouts and SSE streaming.

B. Results

Offline, 48 requests with output lengths uniform[16, 256] ran at 377.2 tok/s with continuous batching at B=32 (n=3, cv ≤ 1.8%); decode-only throughput reaches 517.8 tok/s at B=32 and 670.4 at B=64. With a 587-token shared system prompt, cache hits cut TTFT from 359.8 to 39.6 ms, and batched throughput (B=16) rose from 63.1 to 153.5 tok/s. Under open-loop Poisson load the server's knee lies between 2 and 3 req/s (TTFT p99 0.47 s → 15.5 s), with zero errors in all 66 measured points. Weight-only int8 costs +0.13% perplexity (11.300 vs. 11.286) and speeds batch-1 decode from 42.4 to 51.0 tok/s, with no gain at batch 32.

C. Found by measuring

Three bottlenecks appeared only under measurement. Timing each op of a 102 ms decode step at B=32 found 81 ms in the K/V gather; block-level index_select was 6.4× faster than advanced indexing (+66% throughput at B=32). The first serving sweep collapsed at 128 tok/s because mixed steps padded every decode row to the prefill chunk length; attending decode and prefill rows in separate groups fixed it. Top-p at B=32 was slowed by a per-row CPU multinomial over the 151,936-token vocabulary; inverse-CDF sampling on the device made it 69% faster.

D. Limits

Everything ran on one M2 laptop over localhost, with another job sometimes using the CPU (runs gated at load1 ≤ 4 and repeated 3×); absolute numbers will not transfer to a GPU server. The serving workload is synthetic (log-normal lengths, random-token prompts), and the Ollama comparison is not like-for-like (4-bit GGUF with llama.cpp Metal kernels vs. fp16 eager PyTorch). Single-stream latency is rill's weak spot: per-step Python overhead makes its concurrency-1 TPOT (26 ms) worse than HF generate (17 ms) and Ollama (9 ms). fp16 batching is not batch-invariant: some greedy outputs differ from a sequential run at near-tie tokens (fp32 is exact). There is no fused paged-attention kernel and no multi-GPU support, and the GitHub Actions CI has never run remotely; its steps were run locally.
