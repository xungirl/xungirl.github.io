agent-eval-mcp: An MCP Tool Server, a Hand-Written Agent Loop and the Eval Harness That Measures It

Jiaju Zhang
Northeastern University
github.com/xungirl/agent-eval-mcp
Code ↗Eval results ↗Evidence ↓

Abstract—Tool-calling agents fail in ways a pass rate hides: they write to the database when nobody asked. This project builds a support-operations MCP server (8 tools, refund rules, idempotent writes), a hand-written agent loop with no framework, and an eval harness that scores 36 tasks on the answer, the tool calls, the final SQLite state and safety. On qwen3.8-flash, an explicit policy prompt raised the pass rate from 90.3% to 95.8% as run, with overlapping CIs; the clearer signal is that unauthorized DB writes fell from 6 to 0 in 72 runs.

Index Terms—Model Context Protocol, tool-calling agents, LLM evaluation, agent safety, SQLite, asyncio.

I. The problem

Correct answers, wrong side effects

A support agent that answers correctly can still move money. Checking the final text is not enough: an eval has to look at which tools were called and what changed in the database. It also has to prove that its own scorers are right, or a failing score says nothing about the agent.

II. Design

SupportService holds the business logic in pure Python with no MCP imports: refunds require a delivered order, a 30-day window, at most $500 and at most the remaining balance. The check and the insert run inside BEGIN IMMEDIATE with an idempotency key; tests cover a retry after a lost response (exactly one refund) and 10 concurrent $40 refunds against $54 remaining (only 1 succeeds). The MCP layer only maps arguments in and errors out, and registers write tools only with --allow-writes.

The agent loop owns retries, step limits, a run deadline, per-call timeouts and a tool allow-list, and writes every step to a JSONL trace. Permissions are enforced in three layers: the read-only server, the loop's allow-list and the service. The harness gives every task run its own database copy; six scorers grade it, safety by per-table hashes. Replaying every gold trajectory must score 100% as a CI gate, and a hijacked-agent negative control must fail.

III. Results

Two prompts were compared on one model, 2 repeats per task. The baseline's 6 safety violations included a self-initiated $25.00 refund during a prompt-injection task; the other 5 were tickets nobody asked for. In readonly-refund the improved agent still emitted issue_refund in both repeats, and the allow-list returned permission_denied without forwarding it.

IV. What went wrong

A hard cap of 195 requests per config was hit mid-task in the first real run, cutting off 9 baseline and 3 improved runs, which then counted as agent failures. The fix: a soft budget checked before each run starts, plus --resume, which re-ran only the 12 missing runs (36 requests); the whole evaluation made 434 real requests against a target of about 400. Trace review then showed that all 3 improved-prompt failures were correct refusals the rubric did not list. An offline rescore with zero LLM calls gives 100.0%, but that figure is post-hoc and is quoted only with the as-run 95.8%.

V. Limits

The sample is small and the CIs overlap, so the pass-rate gain is suggestive, not conclusive. The improved prompt is at the ceiling of 36 hand-written tasks; answer checks are rule-based phrase lists with no LLM judge; only one model was evaluated. Latency came from 4 concurrent runs on a shared public API, not a controlled benchmark. The measured runs used the in-process transport; stdio and streamable HTTP are covered by tests only. The server has no authentication.
