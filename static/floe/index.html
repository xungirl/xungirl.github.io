floe: A Columnar SQL Engine in C++20 and a Multi-Tenant Data Platform, Built from Scratch

Jiaju Zhang
Northeastern University
github.com/xungirl/floe
Code ↗Benchmarks ↗Evidence ↓

Abstract—floe is a mini "AI Data Cloud" built from scratch: a C++20 columnar SQL engine with no database libraries inside, a Java 21 multi-tenant, metadata-driven platform on top of it, and a tenant-safe NL→SQL agent. The engine stores data as immutable micro-partitions, prunes them with zone maps and runs vectorized, morsel-driven pipelines. All 11 targeted TPC-H queries return the same results as DuckDB at SF0.01 and SF1, and an adversarial suite of 52 attacks found 0 cross-tenant leaks. floe is also 4.3x–6.1x slower than DuckDB (geometric mean, SF1), as expected from a learning-scale engine. Every number was measured on one laptop.

Index Terms—columnar storage, zone maps, vectorized execution, morsel-driven parallelism, multi-tenancy, NL-to-SQL, OpenTelemetry.

I. The problem

Why rebuild a warehouse at learning scale

A cloud warehouse hides several hard problems behind one SQL box: read as little data as possible, use every core without locks on the hot path, and let many tenants share one physical table without ever seeing each other's rows. floe rebuilds each piece so that each claim can be checked. DuckDB is used only to generate TPC-H data and as a correctness oracle and performance baseline, never inside the engine.

II. Design

Storage. Tables are immutable micro-partitions of 65,536 rows made of per-column chunks. For every chunk the encoder picks PLAIN, RLE, bit-packing or dictionary by the smallest exact encoded size, and each chunk and footer carries a CRC32. Zone maps (min, max, null count, HyperLogLog distinct estimate) live in a versioned manifest, so the planner prunes without opening files. Because files never change, time travel and zero-copy CLONE only write manifests: cloning lineitem takes 3.6 ms vs 6.9 s for a deep copy.

Execution. A hand-written recursive-descent parser feeds a binder, a rule-based optimizer with a greedy, statistics-based join orderer, and push-based pipelines over batches of 2,048 rows with selection vectors. Worker threads claim the next micro-partition from an atomic counter and write thread-local state that is merged once at the end. Table I shows what each rule is worth.

Tenancy. All tenants' records live in one table, mt_data; custom objects and fields are metadata rows that map a field to a slot column, so defining a field never runs ALTER TABLE. Isolation is enforced in exactly two classes: Java TenantScopeBuilder and the engine's ScopedResolver, which hides physical tables behind hidden org_id/object_id filters that SQL can't name. The NL→SQL agent's tools go through the same path, so the model has no more power than the user.

III. Results

Correctness comes first: an oracle script runs the same query text on DuckDB and floe, and 11/11 queries match on both the file-order and the clustered warehouse. The C++ suite passes 74/74 in release, under ASan+UBSan and under TSan, each key suite was green in 10/10 repeated runs, and one request produced one trace of 8 spans across 3 services.

Speed is compared with DuckDB on the same physical layout (Table II). 8 threads are 3.2x–4.5x faster than 1 on the file-order warehouse; the M2 has 4 performance + 4 efficiency cores, so these are not 8 equal cores. With 10 ms + 200 MB/s injected per GET, Q1 falls from 1,392 ms cold to 137 ms from the SSD cache and 0.06 ms from the result cache (Fig. 3).

The NL→SQL agent (Qwen, temperature 0) scored 55/55 with one well-prompted call on the first 55 questions, which proved too easy. On 25 harder questions, written after that set saturated, it scored 19/25 with one call and 18/25 with tools: tools did not beat one good prompt. 30 prompt-injection runs gave 0 leaks and 0 writes.

IV. Limits

Everything ran on one laptop that was not idle (load average 7–14), and the "object store" is a local directory with injected latency, so nothing here is distributed. The SQL subset has no subqueries in WHERE/SELECT, outer joins, set operations or window functions, so only 11 of the 22 TPC-H queries run. Writes are INSERT only, with no compaction or version GC, and the loader keeps a whole table in memory. The GitHub Actions workflow has never run on GitHub; its equivalent ran locally as make ci, so Linux/gcc builds are untested.
